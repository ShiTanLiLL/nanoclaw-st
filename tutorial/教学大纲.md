# NanoClaw 渐进式复现教学大纲

这是一份约 10～20 课的路线图，不是后续教案集合。预热阶段只生成了第 1 课
教案；此后只在进入对应课程时生成该课教案和代码。目前正在进行第 5 课。

## 课程总览

课程从一个可以运行的本地文本闭环开始，每一次增加复杂度都对应一个真实需求。
最终再与原项目的渠道、中心数据库、会话邮箱、容器和调度机制建立对应关系。

## 第 1 课：最小单次对话闭环

- [x] **背景**：项目还不存在，先验证“用户给一句话，助手能给回复”这个最小价值。
- **本课需求**：从标准输入读取一段文字，生成确定的本地回复并输出。
- **任务**：建立 TypeScript 工程；写一个最小回复函数；用一次 Happy Path 测试
  固化输入和输出；提供一次性 CLI 入口。
- **主要技术点**：函数输入输出、Node 标准输入输出、TypeScript 编译、最小测试。
- **预计影响**：`src/reply.ts`、`src/main.ts`、`test/reply.test.ts` 和工程配置。
- **与后续关系**：先不引入消息对象、会话、渠道、模型或数据库；第 2 课会因
  “不是每句话都应该触发助手”而引入触发规则。
- **完成标准**：学生能解释文本从 CLI 到回复函数再到终端的链条，测试通过并手动 commit。

## 第 2 课：只响应真正发给助手的消息

- [x] **背景**：聊天中存在普通闲聊，助手不能对每句话都回复。
- **本课需求**：识别简单触发词（例如 `@Andy`），忽略未触发的文本，并保留用户可见的原文。
- **任务**：先写触发/不触发测试，再在现有函数前增加最小判断。
- **主要技术点**：字符串处理、分支、测试驱动和“忽略”结果的表达。
- **预计影响**：重写第 1 课回复入口；不引入正则框架或配置系统。
- **与上一课关系**：第 1 课的“收到什么都回答”被真实场景推翻。
- **完成标准**：触发消息回复，普通消息不输出，测试覆盖两条路径。

## 第 3 课：一段对话需要记住上下文

- [x] **背景**：用户连续提问时，助手不能把每句话都当作全新请求。
- **本课需求**：在进程内维护一个最简单的当前会话上下文，让回复能看到前文。
- **任务**：增加一个进程内的用户正文数组；规定先读后写的顺序；让 CLI 连续读多行；测试两轮对话。
- **主要技术点**：数组状态、共享可变状态、异步逐行读取、上下文边界。
- **预计影响**：`reply.ts` 接收历史数组，`main.ts` 持续读取；当前不需要 Session 类或接口。
- **与上一课关系**：触发规则已能决定“是否回答”，现在需要回答“基于什么回答”。
- **完成标准**：同一进程内两轮输入的上下文顺序可验证。

## 第 4 课：程序重启后对话不能凭空消失

- [x] **背景**：内存会话在进程结束后丢失，个人助手无法持续使用。
- **本课需求**：将一个会话保存到本地 JSON 文件，启动时恢复。
- **任务**：写重启恢复测试；用一个 JSON 数组保存当前会话；启动时读取、有效消息后写回。
- **主要技术点**：文件 I/O、JSON、失败时的最小处理。
- **预计影响**：出现第一个持久化边界；不提前使用 SQLite 或 Repository。
- **与上一课关系**：内存方案在“重启”需求下暴露生命周期问题。
- **完成标准**：测试真正启动两个进程，第二次能从第一次留下的文件恢复历史。

## 第 5 课：不同聊天不能混用记忆

- [ ] **背景**：同一助手收到多个聊天来源，不能把甲的上下文回答给乙。
- **本课需求**：按本地模拟的 `chatId` 区分多个聊天，每个聊天拥有独立历史。
- **任务**：拆分输入中的聊天地址和正文；建立聊天 ID 到历史数组的映射；
  将 JSON 从单数组改为分组对象并兼容旧文件；测试两个聊天交错发送与重启恢复。
- **主要技术点**：标识符、映射、数据迁移的最小版本。
- **预计影响**：初步出现原项目的 messaging group/session 两层含义。
- **与上一课关系**：单文件单会话不再能满足多聊天隔离。
- **完成标准**：交错消息仍落入正确会话。

## 第 6 课：回复不应阻塞新消息

- [ ] **背景**：真实模型调用耗时，第二个用户不能一直堵在第一个请求后面。
- **本课需求**：将输入和输出放入内存队列，由一个工作循环异步处理。
- **任务**：先测试入队/出队顺序；再引入最小 worker；保留可观察的 pending/processing/completed 状态。
- **主要技术点**：Promise、async/await、事件循环、队列和状态转移。
- **预计影响**：同步调用演化为宿主与处理器之间的消息链。
- **与上一课关系**：长耗时处理让直接调用的边界暴露出来。
- **完成标准**：多个输入可排队，状态和输出顺序可测试。

## 第 7 课：把“收到消息”和“发送回复”分开

- [ ] **背景**：CLI 只是一个入口，未来还要接入 webhook 或真实聊天平台。
- **本课需求**：引入一个具体的本地渠道（仍先使用内存/终端），明确接收和投递边界。
- **任务**：实现一个最小 console channel；测试入站事件和出站回复；只在出现第二种入口前讨论抽象。
- **主要技术点**：事件回调、模块边界、何时值得抽象 Adapter。
- **预计影响**：初步对应原项目 `ChannelAdapter`，但不复制其完整接口。
- **与上一课关系**：队列已有处理链，新的入口需要接到链条两端。
- **完成标准**：渠道只处理平台输入输出，不负责会话业务。

## 第 8 课：数据量增长后需要查询和稳定标识

- [ ] **背景**：JSON 文件查询困难，多聊天并发写入也容易损坏。
- **本课需求**：使用 SQLite 保存用户、聊天、会话和消息的最小数据。
- **任务**：先为最小表写失败测试；迁移已有数据；实现创建、查询和追加。
- **主要技术点**：SQLite、表/行/主键、事务、迁移的动机。
- **预计影响**：教学项目出现中心数据库；只保留当前需求用到的列。
- **与上一课关系**：文件方案在结构化查询和并发下失效，组件由需求推动。
- **完成标准**：重启后查询和交错写入可验证。

## 第 9 课：会话处理需要独立的输入和输出邮箱

- [ ] **背景**：宿主和 agent 处理器同时访问共享状态，双写会产生锁和边界问题。
- **本课需求**：为每个会话建立宿主写入的 inbound 与处理器写入的 outbound 两个邮箱。
- **任务**：先固定消息表和读写方向；实现轮询；测试一进一出和处理确认。
- **主要技术点**：进程边界、单写者、轮询、消息状态和幂等投递。
- **预计影响**：对应原项目 per-session SQLite mailbox，但先不接 Docker 和真实模型。
- **与上一课关系**：中心库负责路由，处理邮箱负责会话内 I/O，职责开始分层。
- **完成标准**：每个数据库只有一个写入者，消息可以完整往返。

## 第 10 课：处理器需要隔离运行环境

- [ ] **背景**：助手要执行工具和读写文件，不能把模型进程的权限直接放在宿主机。
- **本课需求**：用一个最小 Docker 容器运行 agent-runner，并挂载明确的会话目录。
- **任务**：先定义启动输入；实现容器生命周期；保留可替换的测试运行器；验证挂载边界。
- **主要技术点**：Docker、进程生命周期、只读/读写挂载、心跳。
- **预计影响**：对应原项目 `container-runner` 与 `container-runtime`；不提前加入资源限制全家桶。
- **与上一课关系**：双邮箱已经定义了清晰的进程边界，现在才有理由引入隔离。
- **完成标准**：容器能消费输入、写出回复并在空闲时停止。

## 第 11 课：模型调用从假回复替换为真实 Provider

- [ ] **背景**：固定文本只能验证链路，用户需要真正的 AI 生成能力。
- **本课需求**：接入一个真实模型 SDK，并为测试保留一个确定性的本地假模型。
- **任务**：先写 Provider 行为测试；引入真实 SDK；解释为什么第二种实现出现后才抽象 Provider。
- **主要技术点**：第三方 SDK、流式/异步调用、凭据边界、测试替身。
- **预计影响**：对应容器内 provider registry；不会把所有供应商一次装入项目。
- **与上一课关系**：隔离运行链路已稳定，模型才成为可替换的处理步骤。
- **完成标准**：配置真实模型可运行，默认测试无需网络和密钥。

## 第 12 课：一个聊天可以连接多个 Agent 群组

- [ ] **背景**：个人助手和专用助手可能服务同一聊天，且触发规则不同。
- **本课需求**：建立 messaging group → agent group 的 wiring，按 mention/pattern 选择并可扇出到多个会话。
- **任务**：扩展中心数据；实现最小路由策略；测试无触发、单 Agent 和多 Agent。
- **主要技术点**：关系建模、路由、扇出、会话模式。
- **预计影响**：对应原项目 `router.ts` 的核心业务，但省略早期权限模块的全部分支。
- **与上一课关系**：单 Agent 链条无法表达多角色协作，路由配置成为真实需求。
- **完成标准**：每条消息到达正确 Agent，会话记忆互不污染。

## 第 13 课：任务可以在未来或周期时间自动触发

- [ ] **背景**：用户希望助手定时汇报，而不是每次手动发送。
- **本课需求**：用同一消息链支持一次性和周期任务。
- **任务**：增加任务数据与时间字段；实现最小调度循环；测试到期、完成和下一次周期。
- **主要技术点**：时间、调度、幂等、任务状态。
- **预计影响**：对应原项目 scheduling 与 host sweep；暂不加入复杂脚本门控。
- **与上一课关系**：消息邮箱已能处理普通输入，定时任务只是新的消息来源。
- **完成标准**：任务产生的输入能走同一会话处理和投递路径。

## 第 14 课：失败、重试和文件消息不能破坏主链路

- [ ] **背景**：模型、平台和文件都可能失败；一次异常不能让消息永久丢失或重复发送。
- **本课需求**：增加有限重试、处理确认、附件安全路径和投递幂等。
- **任务**：先制造失败测试；实现状态回退和退避；再加入文件白名单/目录边界。
- **主要技术点**：错误分类、重试、幂等、安全的文件 I/O。
- **预计影响**：对应原项目 stale detection、delivery attempts、inbox/outbox safety。
- **与上一课关系**：调度把系统运行时间拉长，失败恢复成为现实问题。
- **完成标准**：可恢复失败不丢消息，重复投递不会多发，越界文件被拒绝。

## 第 15 课：整理成可配置、可部署、可理解的系统

- [ ] **背景**：功能完成后仍需要启动、配置、日志、权限和运维边界。
- **本课需求**：补齐最小配置、日志、CLI 状态查看、权限/审批和部署说明，并与原项目最终结构对照。
- **任务**：按需求逐项整理；画最终心智模型；运行端到端验收；记录哪些原功能主动省略。
- **主要技术点**：配置来源、日志、权限、部署、最终架构复盘。
- **预计影响**：整合教学项目，而不是复制原项目所有脚手架、渠道和技能。
- **与上一课关系**：可靠主链路已经存在，最后才有理由增加运维和治理能力。
- **完成标准**：学生能回答系统业务、数据流、状态流、模块职责、第三方组件和抽象形成原因。

## 推进约束

- 当前只进入第 3 课；第 4～15 课不创建教案文件，不实现其代码。
- 每节课完成后才把对应复选框从 `[ ]` 改为 `[x]`，并更新学习记录与项目地图。
- 未来课程若与当前实现冲突，允许移动、拆分、重写或删除前面代码；这正是
  课程要展示的架构演化。
