# 状态模型

## 消息生命周期

```mermaid
stateDiagram-v2
    [*] --> Pending: 宿主写入 messages_in
    Pending --> Processing: agent-runner claim
    Processing --> Completed: 处理并写出结果
    Processing --> Pending: 容器失败/宿主退避重试
    Processing --> Failed: 超过重试上限
```

`messages_in.status` 由宿主拥有；容器因为只读打开 inbound.db，不能直接改变
它，而是在 outbound.db 写 `processing_ack`，宿主再同步终态。这是“谁拥有状态”
很重要的例子。

## 会话和容器生命周期

```mermaid
stateDiagram-v2
    [*] --> ActiveSession: 首条触发消息
    ActiveSession --> Stopped: 没有运行容器
    Stopped --> Running: requestWake / spawn
    Running --> Idle: 暂无待处理消息
    Idle --> Running: 新消息到达
    Running --> Stopped: 空闲回收或容器退出
    ActiveSession --> Closed: 管理操作关闭会话
```

Session 记录业务身份和容器状态；心跳文件、处理确认和宿主 sweep 共同判断
运行中的容器是否还活着。

## Router 的触发状态

```mermaid
stateDiagram-v2
    [*] --> UnknownChat
    UnknownChat --> Registered: mention/DM 触发自动登记或批准
    UnknownChat --> Ignored: 普通闲聊
    UnknownChat --> NoWiring: 已建聊天但未接 Agent
    NoWiring --> Wired: 管理员创建 wiring
    Wired --> Accumulated: 不触发但策略为 accumulate
    Wired --> Dropped: 不触发且策略为 drop / 权限拒绝
    Wired --> Engaged: 触发且通过权限
    Engaged --> SessionCreated: 找不到对应会话
    Engaged --> SessionReused: 找到已有会话
```

## 第 1 课的状态

第 1 课还没有持久状态或异步状态。每次 CLI 调用都是：

```text
输入字符串 → 调用 replyToText → 输出字符串 → 进程结束
```

因此不画假的 pending/running 状态；状态视角会在第 3 课真正需要上下文时再引入。
