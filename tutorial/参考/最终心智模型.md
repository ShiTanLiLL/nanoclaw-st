# 最终心智模型：教学实现到第15课

## 用户真正得到什么

用终端或文本文件给某聊天发消息，符合触发规则的消息交给一位或多位助手；
各助手带自己的角色和上一句用户正文调用模型，回答回到终端。可让任务未来
自动产生输入，读取公开文本，失败后继续原事件；周期执行必须明确批准。
当前没有联网聊天平台，也没有模型工具调用，不把文本生成器说成完整自动Agent。

## 一条具体消息的旅行

`[课堂] @Andy 解释闭包` → parseChatLine拆出chatId与text → 内存队列接收 →
handleMessage用新事件ID查凭据 → routeMessage选择Andy和可能的Teacher →
文件命令才在宿主展开 → 中央事务保存目标/角色/上一句、更新会话记忆与搜索 →
每个会话入站source_key去重 → processMailbox只读入站 → SDK调用与有限重试 →
出站inbound_id确认 → 宿主输出并写中央投递确认 → 自动链凭据done。
task:<ID>:<next_run>取代随机事件ID，令同一失败轮次能够恢复；正常成功后才
推进任务时间。相同文本的新输入仍有新事件ID，不按文字去重。

## 六种数据身份

| 数据 | 宿主磁盘位置 | 读写责任及用途 |
|---|---|---|
| messages | conversation.db | 宿主写/查；跨聊天搜索的正文投影，非完整事件 |
| session_messages | conversation.db | 宿主写/读；聊天×助手的用户记忆，当前只取上一句 |
| receipts/receipt_targets | conversation.db | 宿主写/读；事件身份、完成状态和原目标快照 |
| inbound.messages | mailboxes/<哈希>/inbound.db | 宿主写，处理器只读；source_key去重交接 |
| outbound.replies | mailboxes/<哈希>/output/outbound.db | 处理器写，宿主读；inbound_id确认已处理 |
| delivered_replies | conversation.db | 宿主写/读；邮箱键×出站编号确认已输出 |

助手回复保存在出站，不进入session_messages；搜索只保存第一排序路由目标
正文一份。多助手正文可能不同，文件正文也可能是展开快照，因此中央搜索不是
无损的原事件存档。配置关系另有agents/wirings/sessions；任务另有scheduled_tasks。

source_key是宿主需要的交接身份，却保存在邮箱：判断邮箱里是否已有这封信，
必须让唯一约束落在那一个独立数据库。容器不读它并不意味着它不应存在。
中央事务不能涵盖多个邮箱，中央凭据存在也不保证所有邮箱都交接过。

中央messages与receipts有数据重复，这是按用途分开的当前取舍，不是唯一架构。
可以把messages扩成完整事件主表，目标与状态挂在它下面，并提供搜索查询；
那样也能恢复。必要的是稳定身份、快照、状态与交接去重，不是表名或表数。
本课不因为解释可替代方案就无需求重构全部存储。

## 执行与权限

宿主：CLI、队列、路由、中央事务、文件安全读取、调度、日志、投递。
处理器：agent-runner → processMailbox → provider → retryTransient。
处理器可在宿主执行，也可显式通过Docker执行。自动聊天/watch/recover默认宿主。
容器只获得当前会话只读输入、可写输出目录、模型配置和必要网络，中央库与
其他邮箱/原附件不挂载。输出文件写操作虽来自容器，实际仍在宿主磁盘。

任务批准是本地所有者对持续请求的确认，不验证聊天发送者，不替代OS目录权限，
更不是工具动作审批。暂停调度不阻止所有者显式执行recover或邮箱处理。
单执行者约定与只读输入不能自动变成跨进程执行锁。

## 模块对照（对应思想，不是接口一一复制）

| 原项目 | 教学模块 | 简化与损失 |
|---|---|---|
| src/index.ts、渠道模块 | main.ts、message-queue.ts | 终端/重放，无平台订阅、线程或卡片 |
| src/router.ts | router.ts | 简化聊天×助手绑定，mention/pattern |
| src/session-manager.ts、src/db | store.ts、router.ts、receipt.ts | 中央SQLite与快照，无远程驱动及复杂迁移 |
| src/mailbox | mailbox.ts、processor.ts | 每会话双邮箱，无完整驱动/claim体系 |
| src/container-runner.ts | container-runner.ts | 单轮容器，无池、心跳、常驻管理 |
| container/agent-runner、Provider | agent-runner.ts、provider.ts、retry.ts | Anthropic文本协议，无工具循环/流式输出 |
| src/delivery.ts | mailbox.ts的deliverReplies | 终端确认，无平台幂等键与附件上传 |
| src/host-sweep.ts | scheduler.ts、main.ts恢复入口 | 一次/固定间隔，无cron/独立任务会话 |
| src/cli、配置、权限/审批模块 | runtime.ts、任务状态命令、.env | 只读统计和本地周期批准，无用户/角色/OneCLI |

## 为什么组件是逐渐出现的

函数足够时只用函数；需要上一句才有内存历史；重启才有文件；跨聊天查询才有
SQLite；跨进程交接才有双邮箱；隔离运行才有Docker；真实模型和测试替身都存在
才有ReplyProvider函数约定；多助手才有会话关系；未来输入才有任务表；部分失败
才有凭据和重试；持续收费和观察需求才有批准门和运行日志。
没有Repository/Factory/Plugin框架。模块拆分按出现的职责边界，不按原项目目录抄写。

## 不承诺的能力

不保证API成功但未写出站、stdout输出但未写确认等崩溃窗口下恰好一次；
不支持多个并发宿主争抢任务；不自动跳过同邮箱的永久错误消息；不限制所有者
显式恢复的总费用；不检查云端可用性、不统计token计费、不提供实时进程健康。
日志默认关闭且仅固定事件脱敏，完整错误栈和业务输出仍可能包含私人信息。
私人数据不进Git，结课提交不是完整运行数据备份。

## 最终验收问题

1. 一条消息为什么可能对应两个会话？聊天ID、助手ID、会话ID、邮箱键区别？
2. 搜索消息、会话上一句、恢复凭据、入站和出站分别为谁服务？
3. source_key、inbound_id、outbound_id分别保护哪一步重复执行？
4. 谁改变任务状态，谁改变凭据状态？暂停为什么不是取消在途请求？
5. 自动模式在哪调用模型？容器实际能读取哪些文件？
6. status的valid和任务pending是否意味着云端成功或watch在运行？
7. 每个模块和第三方组件为什么在那一课才引入？哪些功能没有复现？

由学生按具体例子回答并反馈，不能由Agent填写“学生已掌握全部”。
