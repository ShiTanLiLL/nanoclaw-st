# 原项目分析：NanoClaw v2

## 1. 项目到底解决什么问题

NanoClaw 是面向个人的 AI 助手宿主。使用者从一个或多个聊天平台发送消息，
宿主把平台身份和聊天地址映射到某个 Agent 群组及其会话；隔离容器中的
agent-runner 读取消息，调用 Claude 或其他已安装 Provider，产生文字、卡片、
文件或系统动作；宿主再把输出交回正确的平台。它追求“足够小、能读懂、靠
操作系统容器隔离”，而不是通用多租户 SaaS。

用户需要它的原因有两点：一是用聊天入口调用具有文件、网页和工具能力的个人
Agent；二是让 Agent 的工作区、凭据和工具执行与宿主机隔离，同时保留每个会话
的记忆和可调度任务。

## 2. 最重要的 Happy Path

一次普通消息的主链路为：

```text
平台消息
→ 渠道适配器提取 channel/platform/thread 和消息内容
→ 宿主 router 查 messaging_groups
→ 找到 wiring 的 agent_group 和 engage 规则
→ resolveSession 找到或创建会话
→ 宿主写入该会话的 inbound mailbox
→ requestWake 启动/唤醒对应容器
→ agent-runner 轮询 inbound，批量格式化上下文并调用 Provider
→ agent-runner 写入 outbound mailbox
→ 宿主 delivery 轮询 outbound
→ 渠道适配器投递到原平台
```

其中“普通回复”是最值得先教学的主干；审批、附件、调度、Agent-to-Agent、
多实例渠道和自修改都是主干之上的分支。

## 3. 核心用户/实体

- **User**：命名空间化的平台身份，如 `telegram:123`、`discord:456`。
- **Messaging Group**：某个平台上的一个聊天/频道，由 `channel_type + platform_id + instance` 标识。
- **Agent Group**：一套工作区、人格、技能和容器配置；多个会话可共享它。
- **Wiring**：Messaging Group 与 Agent Group 的连接，包含触发模式、发送者范围、
  忽略策略和会话模式。
- **Session**：一个 Agent Group 在某聊天/线程下的连续上下文和一个运行容器。
- **Message In/Out**：宿主到 Agent、Agent 到宿主的消息记录；所有内容（聊天、
  任务、系统动作、Agent-to-Agent）都尽量统一为消息。

## 4. 复杂度真正来自哪里

1. 平台种类和平台线程语义不同，必须有渠道适配器和路由层。
2. 多聊天、多线程、多 Agent 扇出要求 Session 查找不能只靠一个全局会话。
3. 宿主和容器是不同进程，且不应共享双写的 SQLite 文件，所以形成中心库、
   每会话双邮箱和单写者约束。
4. 模型调用是异步、昂贵且可能失败的，容器需要轮询、批处理、继续会话、心跳、
   stale detection、重试和输出投递。
5. Agent 可以发送系统动作、文件、卡片、任务或其他 Agent 消息，宿主必须把
   这些动作当作不可信请求来验证和执行。
6. 真实安装需要 Docker、OneCLI、渠道技能、迁移、日志和服务生命周期；这些
   工程复杂度不是最初业务价值所必需的。

## 5. 核心状态

- 入站消息：`pending → processing → completed/failed`，容器只写 outbound
  的 processing ack，宿主镜像回 inbound 状态。
- 会话：`active`，容器状态可为 `stopped → running → idle → stopped`。
- 出站消息：未投递 → 已投递，失败会记录尝试次数，超过上限后放弃并保留失败痕迹。
- 渠道注册：未知聊天可自动建立 Messaging Group；无 Agent wiring 时记录丢弃或
  发起审批，显式拒绝后静默丢弃。

## 6. 关键边界

- 中心 DB：路由和实体，不保存全部会话内容。
- `inbound.db`：宿主写，容器读；包含 `messages_in`、routing、destinations、delivery 记录。
- `outbound.db`：容器写，宿主读；包含 `messages_out`、processing ack、会话继续信息、容器状态。
- Agent 群组目录：CLAUDE.md、技能和工作文件，按容器挂载规则暴露。
- Docker 容器：执行模型和工具，只有显式挂载路径可见。

## 7. 教学解释顺序

先用第 1～7 课建立“消息进来、处理、出去”的业务直觉，再逐步引入第 8～10
课的持久化、双邮箱和隔离；第 11～15 课才解释 Provider、路由扇出、调度、
可靠性和运维。这样学生能回答“为什么需要它”，而不是先背最终目录。
