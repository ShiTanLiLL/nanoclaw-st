# 第 9 课：让宿主与处理器通过邮箱交接

## 1. 前言

第 8 课已经有了一张中心消息表：终端收到一行，马上查上一句、生成回复、保
存正文并输出。这一切发生在一个进程里，非常顺畅。现在设想助手的处理器是
**另一个进程**：宿主收到消息的时候，处理器可能还没启动；处理器做完的时
候，宿主也可能要过一会儿才来取回复。函数参数和进程内的队列都没法跨进程
保存这次交接。更进一步，如果双方都直接修改同一个邮箱文件，"谁负责确认、
谁负责写入"也会变得模糊。

本课先在本地模拟这两个角色，不引入 Docker，也不引入真实模型：宿主把消息
投入该聊天的输入邮箱，处理器从输入邮箱读取、把回复放进输出邮箱，宿主再
取走并输出。这三个动作可以由三个 Node 进程先后完成；原来的终端和文件入
口仍然会自动把三步串起来。这里暂时把一个 `chatId` 当作一个会话的地址，
真正的会话实体和生命周期还没有出现。

## 2. 主要内容

### 2.1 本课做什么

1. 每个聊天在 `mailboxes/` 下获得自己的目录，里面是 `inbound.db` 和
   `outbound.db` 两个 SQLite 文件。
2. 宿主只写 `inbound.db`：记录原始的 `@Andy` 文本，以及**接收当时**的上
   一句。宿主继续把用户正文写进第 8 课的中心库，供搜索和后续回顾使用。
3. 处理器只读输入邮箱、只写输出邮箱。它查询尚无回复的输入行，调用
   `replyToText()`，并用 `inbound_id` 把回复与输入一一对应起来。
4. 宿主只读输出邮箱，打印尚未投递的回复。投递确认写在宿主拥有的中心库
   `delivered_replies` 表中，不会反过来修改处理器的输出邮箱。
5. 增加 `--receive`、`--process 聊天ID`、`--deliver 聊天ID` 三个单次命
   令，并用测试验证它们能跨进程交接；原有自动运行模式保留。

### 2.2 按函数读代码

收信链：

```text
runReceive() 或 runCli()/runReplay() 收到一行
→ processMessages() 把行交给旧的内存队列
→ parseChatLine() 得到 chatId 与 text
→ triggeredBody() 判断是否真的呼叫助手，得到不带 @Andy 的正文
→ lastUserMessage() 从中心库读该聊天上一句
→ enqueueInbound() 把 text + previousMessage 写进该聊天 inbound.db
→ appendUserMessage() 把正文写进中心库 messages 表
```

处理链：

```text
--process 家人 → runProcess('家人')
→ processInbox() 只读家人的 inbound.db
→ 对每行按 inbound_id 查 outbound.db：已存在则跳过
→ replyToText(text, previousMessage) 产生 { body, reply }
→ 只把 reply + inbound_id 插入 outbound.db
```

投递链：

```text
--deliver 家人 → runDeliver('家人') 打开中心库
→ deliverReplies() 只读家人的 outbound.db
→ wasDelivered() 查中心库中有没有该 outbound_id 的确认
→ 没有则输出 reply，再调用 markDelivered() 写确认
```

正常直接运行或 `--replay` 时，`processMessages()` 会在每条有效消息入站后
**立刻**调用 `processInbox()` 和 `deliverReplies()`，所以旧的用法仍然能
立即看到回复。这只是本地演示把三步串在了一起；跨进程测试则使用三个独立
命令，证明邮箱确实保存了交接数据。

相对上一课，消息处理链中插入了**输入邮箱 → 处理器 → 输出邮箱**三个环
节；`--receive/--process/--deliver` 就是这条链分开运行的三个入口，并没有
新增模型能力。

## 3. 技术要点

### 3.0 环境与引入理由

本课沿用 Node 22.13+、TypeScript 和第 8 课的内置 `node:sqlite`，不安装新
依赖。第 8 课的中心库适合搜索、记住各聊天的用户正文；但进程内的函数调用
不能充当两个进程之间的持久交接。输入/输出邮箱要解决的正是：**谁写、谁
读、断开运行之后数据还在不在**。现在只用到了建表、只读打开、插入、查询和
唯一约束，不引入容器、常驻守护进程或通用消息总线。运行 `pnpm test` 会编
译并执行包含跨进程场景的测试。

### 3.1 坐标：三个数据位置与角色

```text
宿主接收层：CLI / 文件 → 队列 → parseChatLine
      │                       │
      │ 写                    │ 写用户正文 / 投递确认
      ▼                       ▼
该聊天 inbound.db          conversation.db（中心库）
      │ 处理器只读             ▲ 宿主只写；处理器不访问
      ▼                       │
处理器：processInbox → replyToText
      │ 只写                  │ 宿主只读出站，输出后记确认
      ▼                       │
该聊天 outbound.db ───────────┘
```

`mailboxes/` 是运行命令时工作目录下的新数据目录，与 `conversation.db` 一
样被 Git 忽略。这里的"单写者"说的是**角色职责**：宿主写中心库和入站，
处理器写出站。直接模式虽然把两个角色放在同一个进程里先后调用，读写的边
界也保持一致。

### 3.2 代码：每个函数在交接中做什么

- `triggeredBody(text)`：输入不带聊天前缀的文本；普通聊天返回 `null`，
  有效呼叫返回去掉 `@Andy` 的用户正文。宿主只用它来决定是否入站；处理器
  仍然调用 `replyToText()` 得到真实回复。
- `mailboxPaths(baseDirectory, chatId)`：把聊天 ID 哈希成固定的目录名，
  返回入站和出站两个文件的路径。之所以不能把用户给的聊天 ID 直接拼进路
  径，是因为含 `/` 或 `..` 的名字可能改变目录位置。
- `enqueueInbound(...)`：宿主创建聊天目录和输入表，插入 `text` 与
  `previous_body`；它不写输出邮箱。
- `processInbox(baseDirectory, chatId)`：执行一次**单次轮询**，读取当前
  已有的全部输入行；对还没有对应出站行的输入调用 `replyToText()`，然后
  插入输出行。它不修改输入行的状态。
- `deliverReplies(baseDirectory, chatId, database)`：读取输出行，查中心库
  的投递确认，只输出未确认的回复，之后调用 `markDelivered()`。它不修改输
  出行。
- `runReceive()`、`runProcess()`、`runDeliver()`：CLI 的三种独立入口。第
  一个读标准输入，后两个各自需要聊天 ID；`--process` 只查一轮，不是常驻
  的后台服务。
- `processMessages()`：旧的实时/文件链与仅收信链的共同入口。当
  `autoProcess=true` 时，它会把后两步接上，保持前八课的行为。

### 3.3 数据：同一句话的不同形态

假设第一次收到 `[家人] @Andy 我叫小李`，第二次收到
`[家人] @Andy 我刚才说了什么？`，在处理器开始之前：

| 位置 | 第一行 | 第二行 | 谁写 |
|---|---|---|---|
| 中心库 `messages` | `id=1, chat_id=家人, body=我叫小李` | `id=2, ..., body=我刚才说了什么？` | 宿主 |
| 家人 `inbound.db` | `id=1, text=@Andy 我叫小李, previous_body=NULL` | `id=2, text=@Andy 我刚才说了什么？, previous_body=我叫小李` | 宿主 |

处理之后，家人 `outbound.db` 里会有
`{id:1, inbound_id:1, reply:'NanoClaw: 我叫小李'}` 和
`{id:2, inbound_id:2, reply:'NanoClaw: 你刚才说：我叫小李'}`。投递之后，
中心库 `delivered_replies` 里出现 `(家人,1)` 和 `(家人,2)`。要注意，另一
个聊天也可能有自己的 `outbound_id=1`，所以确认键必须是
**`chat_id + outbound_id`** 的组合，单看 `outbound_id` 不够。

再区分几个容易混淆的字段：`body` 是去掉触发词、用于搜索和回顾的用户正
文；`text` 是保留触发词、供处理器重新判断的原始消息；`reply` 才是助手的
输出。`previous_body` 则是**收信那一刻的快照**——正因为如此，就算处理器
晚一些才启动，也能按消息抵达的顺序正确回答两轮问题。

### 3.4 状态：确认保存在哪里

```mermaid
stateDiagram-v2
    [*] --> Inbound: 宿主插入输入邮箱
    Inbound --> Outbound: 处理器插入对应回复
    Outbound --> Delivered: 宿主输出并写中心库确认
    Outbound --> Outbound: 尚未投递，下一次仍能取到
    Delivered --> Delivered: 再次轮询时跳过
```

输入/输出行本身不会来回修改状态："处理过"由 `inbound_id` 在输出表中出
现来表示；"投递过"由 `chat_id + outbound_id` 在中心库确认表中出现来表
示。前者由处理器拥有，后者由宿主拥有。这样安排之后，每个邮箱数据库就都
只有一个写入角色。

### 3.5 流程图：两侧通过磁盘交接

```mermaid
sequenceDiagram
    participant U as 用户/终端
    participant H as 宿主
    participant I as 入站邮箱
    participant P as 处理器
    participant O as 出站邮箱
    participant C as 中心库
    U->>H: [家人] @Andy 我叫小李
    H->>C: 读取上一句
    H->>I: 写 text + previous_body
    H->>C: 写用户正文
    P->>I: 只读待办输入
    P->>P: replyToText()
    P->>O: 写 reply + inbound_id
    H->>O: 只读未确认回复
    H-->>U: 输出 reply
    H->>C: 写投递确认
```

### 3.6 细节技术点

**进程边界与轮询**：进程 A 里的普通变量，进程 B 是不能直接读取的；两者
先后启动时，进程 A 甚至可能已经退出。SQLite 文件把交接内容留在了磁盘
上，这个问题才得以解决。`processInbox()` 是"来看一次有没有新信"的单次
轮询，不是每隔一秒自动醒来的无限循环；想继续处理新信，需要再执行一次
`--process`。常驻运行、唤醒机制和容器，留到真正需要时再做。

**`readOnly: true` 与单写者**：`new DatabaseSync(file, { readOnly: true })`
让打开数据库的这一侧只能读。处理器以只读方式打开入站邮箱；宿主以只读方
式打开出站邮箱。建表、写行则由另一个角色负责。这样，"谁确认处理、谁确
认投递"就不用再靠双方抢着修改同一张表了。

**哈希目录名**：`createHash('sha256').update(chatId).digest('hex')` 把任
意的聊天名字变成固定长度的十六进制字符串。用它是为了安全、确定地生成目
录名，不是为了加密聊天内容，也不意味着聊天 ID 可以被忽略——CLI 仍然必
须提供原始聊天 ID，才能找到对应的目录。不同聊天的邮箱由此分开。

**唯一约束和跳过重复**：输出表的 `inbound_id INTEGER NOT NULL UNIQUE` 说
明一封入站信只能有一封对应的出站回复。处理器先查是否已有回复，所以重复
执行 `--process` 会跳过；宿主用中心库的复合主键记录投递，重复执行
`--deliver` 也会跳过。要说清楚边界：当前测试证明的是**正常重复运行时不
重发**，并不等于任何故障下都"恰好一次"。

**跨文件的失败窗口**：入站与中心库是两个不同的数据库，目前没有横跨它们
的原子事务；如果程序恰好在两次写入的中间崩溃，就可能出现两边数据不一致
的情况。同样，如果程序在输出到终端之后、写入投递确认之前崩溃，下次也可
能再次输出。真实渠道还会有网络失败。这些限制先诚实地记录下来，等后续课
程出现实际的失败恢复需求时再处理，不假装本课已经解决。

## 4. 测试与验收

### 4.1 分离进程的来回交接

**测什么、为什么测**：`--receive`、`--process`、`--deliver` 分别在独立的
Node 进程中运行；这证明交接不是靠内存变量完成的。输入两轮"家人"和一轮
"工作"，可以顺带验证不同聊天的邮箱不会串线。

**输入**：家人先说"我叫小李"，再问"我刚才说了什么？"；工作说"项目顺
利"。

**预期**：只收信时没有任何回复；没处理就先投递，也没有回复；处理家人之
后，只投递出家人的两句正确回复；处理工作之后，只投递出工作的回复。重复
处理和重复投递都不会重复输出；中心库仍然能搜索到工作的正文。

**证明**：三段流程可以跨进程完成，处理确认与投递确认分别有效，旧的搜索
数据没有丢失。

### 4.2 旧链回归

**测什么、为什么测**：内部环节被改造之后，直接终端输入、文件重放、旧
JSON 迁移、聊天隔离和普通消息忽略这些旧能力仍然应该成立。

**输入**：现有 `reply`、`persistence`、`replay`、`search` 等测试的输入。

**预期**：`pnpm test` 的 12 个测试全部通过；项目仍然不需要网络或
Docker。

**证明**：本课改变的是进程间的交接方式，而不是用户已经学会的触发、记忆
和搜索规则。

学生验收时，请画出"宿主写哪两个库、处理器写哪个库"，并解释为什么入站
表不需要再被处理器改成 `completed`，以及为什么两次 `--deliver` 只输出一
次。运行测试并反馈问题之后，再由学生手动提交本课。

## 5. 总结

上一课的一条直接函数链，现在多了两个持久邮箱。宿主负责接收与投递，处理
器负责生成回复；一侧写入的行由另一侧只读，确认保存在负责写入的那一侧。
由此，宿主和处理器可以在不同进程、不同时间先后运行，而原有的自动模式仍
然能即时回复。

本课只做了单次轮询与本地确定性回复：没有 Docker，没有真实模型，没有常驻
唤醒，也没有跨数据库事务或故障下严格的恰好一次。等后续需要让处理器执行
工具和调用模型时，权限隔离的现实需求才会推动容器真正出现。
